# kbool — план ревью, оптимизации и укрепления безопасности

Рабочий документ. Машиночитаемый трекер задач — в [`optimization_ledger.json`](optimization_ledger.json)
(единственный источник правды для статусов). Этот файл — человекочитаемое описание.

## Как пользоваться леджером

- Каждая задача имеет `id` (например `P1.3`), `component`, `category`, `severity`, `status`,
  `files` (с номерами строк), `problem`, `fix`, `acceptance`, `depends_on`.
- Обновляй `status`: `todo → in_progress → done` (или `blocked` / `wontfix`).
- Не понижай тестовый baseline: после каждой задачи прогоняй затронутый набор тестов.
- **Каждая подпапка (kcl, kklass, kkore, ktests) — отдельный git-репозиторий (submodule).**
  Коммить внутри submodule, затем обновляй указатель в суперпроекте.

## Ключевой вывод по `eval` (твой главный вопрос)

kklass — это **кодогенератор**: тела методов хранятся строками и материализуются через `eval`
и `source <(sed)`. Для доверенного кода классов это нормально (аналог компиляции). Опасность —
только когда в генератор попадают **недоверенные данные**. Такие места найдены и разложены по задачам:

- **Реальная RCE (critical):** `string.toInteger`/`toInt64` в kcl выполняют `$(( ... ))` над
  произвольным вводом → `a[$(cmd)]` исполняет `cmd`. → **P1.3**
- **Инъекция имён (high):** `kk._build_class_runtime` не валидирует имена перед `eval`. → **P1.1**
- **Хрупкий `eval` в кэше методов (medium):** заменяется на nameref. → **P1.2**
- **По дизайну, но задокументировать:** format-строка, `bash -c` в ассертах ktests. → **P1.7**

Вывод: **для обычного использования (ты сам пишешь классы) — да, безопасно.** Небезопасно
становится ровно в тех местах, где значения/имена приходят снаружи; их и чиним.

## Фазы (порядок — по зависимостям и ценности)

- **P0 — Зелёный baseline.** Чиним корневую причину флейки (`kv.new`, P0.1) → набор проходит стабильно.
- **P1 — Безопасность (eval/инъекции).** Твой приоритет №1. Критичная RCE в kcl, валидация имён в
  kklass, устранение `eval` из горячего пути, `echo -e → printf`, карантин legacy-модулей.
- **P2 — Ядро kkore.** Фрейм-стек выполняется на **каждом** вызове метода — самый общий рычаг
  производительности; плюс правки корректности (коды возврата, RESULT-конвенция).
- **P3 — Скорость kklass.** Убрать `source <(sed)` на каждый объект (главный вклад в 36с).
- **P4 — Баги фреймворка ktests.** Чтобы результатам тестов можно было доверять (auto-restore не
  срабатывает; список упавших файлов в потоковом режиме пуст; фильтр тестов игнорируется).
- **P5 — Скорость и корректность kcl.** Форк `printf` на символ в хеше, `basename` на запись в
  рекурсии, лишний ре-парс аргументов, пре-заполнение массива в tlist, предсказуемый temp в tfile.
- **P6 — Покрытие тестами.** Добавить тесты, которые ловили бы находки выше (инъекции, edge,
  большие входы, поведение через fork). Только tcustomapplication сейчас имеет security-тесты.
- **P7 — Финальная валидация.** 0 падений на всех компонентах, 3/3 стабильных прогона, сравнение
  времени до/после.

## Приоритетная выжимка (если делать по одному)

1. **P1.3** — RCE в `string.toInteger`/`toInt64` (critical, kcl).
2. **P0.1** — флейки `kv.new` (делает набор зелёным + это же perf-фикс).
3. **P1.1** — валидация имён в `kk._build_class_runtime`.
4. **P2.1** — оптимизация фрейм-стека (общий perf-рычаг для kklass и kcl).
5. **P3.1** — убрать `source <(sed)` из `.new()` (главный вклад в медленный kklass).

## Порядок исполнения по каждой задаче

1. Прочитать `problem` и файлы из `files`.
2. Внести правку минимальным диффом, в стиле окружающего кода.
3. Прогнать затронутый набор тестов; при security/correctness-фиксе — сперва добавить тест,
   который **падает до** правки и **проходит после** (см. `acceptance`).
4. Обновить `status` задачи в леджере.
5. Не трогать публичный API без явного согласования (в задачах это отмечено).
